# ADR: Native Security Boundary (TASK-0.4)

- **Status**: accepted
- **Refs**: REQ-4, SEC-1, SEC-2, SEC-4; design.md §Tauri Security Design

## Context

Phase 0 needs a native security boundary before any feature (auth,
local cache) can be built on top of it: least-privilege Tauri
capabilities, OS-backed secure storage for session/credential material,
and a way to encrypt sensitive local payloads without exposing key
material to the webview.

## Capabilities (SEC-1)

`src-tauri/capabilities/default.json` grants only:

- `core:default` — window/app basics (metadata, event listeners,
  window management). Audited against the pinned `tauri` 2.11.5 crate
  source (`permissions/app/autogenerated/reference.md` etc.): no
  filesystem, shell, SQL, notification, or HTTP reach.
- `allow-session-store`, `allow-session-load`, `allow-session-clear`,
  `allow-encrypt-value`, `allow-decrypt-value` — the five app commands
  this task adds, auto-generated by `tauri-build`'s
  `AppManifest::commands(...)` in `build.rs` (identifiers follow the
  `allow-$command` / `deny-$command` convention for unprefixed,
  app-level commands, command names kebab-cased).

**`tauri-plugin-opener` was removed** (it shipped in the TASK-0.1
scaffold with a default `opener:default` permission that allows opening
*any* `http://`/`https://`/`mailto:`/`tel:` URL — the exact "generic,
unscoped" grant SEC-1 and design.md's "external URL opening uses an
allowlist" rule forbid). Nothing in the app opens URLs yet, so the
least-privilege choice is no grant at all rather than a broad one. It
returns with a narrowly scoped, explicit allowlist when a real feature
(e.g. tender document links, INT-4) needs it.

No filesystem, shell, SQL, notification, or updater permission is
granted anywhere yet. Those are added by the task that actually needs
them (TASK-0.5 for scoped SQL access, a later document-handling task
for scoped filesystem access), each with its own least-privilege scope
— not opened up in advance.

## Secure storage (SEC-2)

Session/credential values go through `security::secret_store`:

- `SecretStore` trait (`set`/`get`/`delete` by key) so the rest of the
  codebase never depends on a concrete backend.
- `OsKeychain` — the real implementation, backed by the `keyring` crate
  (v4, default `v1` feature). That feature pulls in Windows Credential
  Manager (`windows-native-keyring-store`, the v1 product target),
  macOS Keychain (`apple-native-keyring-store`), and a **pure-Rust**
  zbus-based Secret Service backend on Linux
  (`zbus-secret-service-keyring-store`) — confirmed from the crate's
  published dependency manifest before adding it, since no
  `libdbus-1-dev` or other system package is needed to `cargo check`
  this repository on Linux CI/dev machines, even though the shipped
  product targets Windows only.
- `InMemorySecretStore` — process-memory-only, used exclusively by unit
  tests. A real OS credential service isn't guaranteed to be running in
  a headless CI container, so tests never depend on one.

Both implementations validate key length (1–128 chars) and value length
(1–8192 bytes) before touching storage, and every fallible path returns
`SecurityError`, never the underlying platform error text (some
backends can echo call arguments in diagnostic messages).

`session_store` / `session_load` / `session_clear` (`commands/session.rs`)
expose exactly three session slots (`SessionKey::AccessToken` /
`RefreshToken`) — a closed enum, not a free-form string key, so the
secure-storage surface stays auditable. Production authentication stays
disabled (REQ-4) until the Phase 1 native auth contract (TASK-1.3) is
accepted; this task only builds the storage boundary TASK-0.9's auth
feature will call into.

## Local payload encryption

`security::encryption::encrypt_value` / `decrypt_value` (exposed as the
`encrypt_value` / `decrypt_value` commands) implement AES-256-GCM over
an arbitrary string, for local-only payloads such as the SQLite cache
entries TASK-0.5 will add. The data-encryption key is generated on
first use (`Aes256Gcm::generate_key`), persisted through the same
`SecretStore` boundary, and never returned to the webview — only base64
`nonce || ciphertext` crosses IPC. A fresh random nonce is generated per
call (`Aes256Gcm::generate_nonce`), and tampering is rejected by AES-GCM's
authentication tag (tested in `encryption.rs`'s unit tests).

## Content Security Policy (SEC-4 adjacent)

`tauri.conf.json`'s `security.csp` was `null` (no policy) in the
TASK-0.1 scaffold. It now sets:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self' data:;
connect-src 'self' ipc: http://ipc.localhost;
object-src 'none'; base-uri 'self'; form-action 'self'
```

`script-src 'self'` forbids any remote script source, per design.md.
`style-src` keeps `'unsafe-inline'` because component libraries planned
for the accessible foundation (REQ-1) commonly set inline `style`
attributes for dynamic positioning; this is a materially lower-risk
allowance than inline script execution. **`connect-src 'self'` will
need to grow to include the audited parent API origin once TASK-0.7
wires the real transport** — it must be the specific audited origin,
never a wildcard.

## Updater (SEC-4)

No updater plugin is wired up yet — there is no signing key to verify
against. `src/app/config/schema.ts` (TASK-0.3) already reserves an
`update.channel` / `update.publicKey` placeholder for when this is
implemented; the private signing key remains CI-only per SEC-4 and is
never referenced from this repository.

## Deferred to later tasks

- Scoped SQL/filesystem access — TASK-0.5 and a future document task.
- URL-opening allowlist — whichever feature first needs it.
- Full auth feature wiring — TASK-0.9, gated on TASK-1.3.
